# Single tomato-carton pilot

1. Configure Neon, run migrations, bootstrap an admin and start the API.
2. Create a tomato batch with variety, starting ripeness and source in attributes.
3. Register one real ESP32 device. Store the returned credential securely.
4. Burn in/warm up the actual gas module and record a clean-air raw ADC baseline
   using `POST /api/v1/devices/{id}/baseline` before putting it in the carton.
5. Create a `start_condition` observation with starting condition and weight.
6. Send readings every five minutes using the documented public HTTP contract.
   Verify distinct source and ingestion timestamps, retries and warm-up flags.
7. Add daily `routine` observations: condition, firmness, mould, weight and a
   photo reference. Photo references are metadata only; this backend does not
   upload, fetch or store image files. Corrections are new referenced records.
8. After the full configured window, request an assessment. A missing baseline,
   stale/gapped data, unfilled window or unsupported commodity gives insufficient
   evidence. Check data quality before interpreting a risk score.
9. Record a `final_outcome` observation and archive the batch when the pilot ends.

Assessments can be requested explicitly or generated by the monitoring runner
(`python -m app.monitor --actor-user-id YOUR_ADMIN`). It evaluates active monitored
batches every five minutes, including disconnected devices, and records the named
administrator as actor. Priorities check source freshness at query time. Keep the
monitoring and optional AI worker running for continuous operations.

The illustrative policy is a pipeline demonstration, not validated produce science.
The MQ-135 responds to multiple influences; gas rise can reflect tomato ripening.
One carton is one sample and cannot establish predictive accuracy. Keep raw readings
and operator observations for later outcome-based validation. Require human review
before any consequential handling, sale or disposal action.
